# K4110440：面向 3D XPoint 单元数据读写的静态分析

**已找到并恢复一组 16 字节介质数据读写候选通路。** 它包含地址参数、端口/目标选择、四个数据字、命令提交、完成轮询，并被“写入图案后读回比较”和“读出、修改、写回”的代码实际调用。这比仅有 PHY 初始化寄存器或字符串证据更接近本次目标。

已证实的是固件向控制器内部介质接口提交数据读写的代码行为。尚未证实这些访问如何转换成外部 3D XPoint 引脚上的命令，也没有恢复存储单元的行/列/阵列地址定义。不能把下面的控制器 MMIO 地址当作 AHU14132 芯片内部寄存器编号，或可从主机直接写入的地址。

分析全程只读取文件、反汇编并追踪数据流。未加载/执行 DLL，未执行固件或目标模拟器，未运行更新器，未访问硬件。数值校验仅计算独立转写的位运算表达式。

## 1. 分析对象与证据位置

原 DLL `SB_K4110440_x64.dll` 是 x64 PE32+；本轮研究的是其内嵌 ARM/Thumb 固件，不是 Windows 导出的更新器函数。

| 对象 | SHA-256 |
|---|---|
| 原 DLL，1,622,376 字节 | `254e2b87f2f85435dc83798b634345a402a2212d8e64bb80bbe85cf6a0b68857` |
| 提取固件，585,728 字节 | `0a42b2e10bd725f3eecdbdbf52fd4fc4c7581887a5fe94c0cecb3561f600a7ee` |

固件位于 DLL 文件偏移 `[0xEA0D0, 0x1790D0)`。内嵌固件签名的数学验证已在第一轮通过；这不等于验证证书信任或证明芯片型号。DLL 三个导出主要提供固件配置、映射和二进制，不直接提供单元数据读写 API。

本报告中的地址均为固件链接地址，依据 EFLI 段表建立对应关系；硬件运行时地址未实测。

| 段 | 链接基址 | 完整固件起始偏移 | DLL 文件起始偏移 |
|---|---:|---:|---:|
| PBUF | `0xBA000` | `0x400` | `0xEA4D0` |
| VBUF | `0x400000` | `0x3BC00` | `0x125CD0` |

PBUF 函数的段内偏移 = 地址 − `0xBA000`；VBUF 对应减 `0x400000`。再加上表中起始偏移即可回到原始字节。

## 2. 已恢复的读写入口与参数

| 用途 | 固件调用链 | 内部操作码 |
|---|---|---:|
| 读出 16 字节 | `E2B14 → E2DC0 → E7AFC → E7942` | `0x0` |
| 写入 16 字节 | `E2C10 → E2DD6 → E7A1C → E7942` | `0x2` |
| 另一种写入流程 | `E2C40 → E2DF6 → E7AB2 → E7942` | 先 `0x2`，后 `0xB` |

这些名称是分析标签。三种入口共同参数为：`r0=port`、`r1=target`、`r2=address`、`r3=16字节缓冲区指针`。读入口在栈上传入参数 A；写入口在栈上传入 A、B、flag。A/B/flag 的电气或介质模式含义尚未确定。

低层 `E7942` 接收 `ctx, port, target, address, data_ptr, A, B, flag, opcode`。它检查 `port<2`、`target<8`。函数保存寄存器并分配栈后，`data_ptr/A/B/flag/opcode` 分别由 `sp+0x24/0x28/0x2C/0x30/0x34` 取出；flag 取一个字节。这些位置用于复查参数传递，不能与函数入口时的原始栈位置混用。

## 3. 控制器内部寄存器窗口

构造调用 `CF25E → E74CC` 明确传入首窗口 `0x03810000` 和步长 `0x10000`，循环建立两个窗口对象。`D2C70` 保存基址；context 通过全局绑定链交给读写包装函数。两个基址并非只从字符串或孤立常量猜测得出。

| 用途 | 窗口偏移 | port 0 地址 | port 1 地址 |
|---|---:|---:|---:|
| 状态，检查 bit 0 | `+0x08` | `0x03810008` | `0x03820008` |
| 命令提交字 | `+0x1C` | `0x0381001C` | `0x0382001C` |
| 编码后的地址参数 | `+0x20` | `0x03810020` | `0x03820020` |
| 读数据：四个 32 位字 | `+0x30,34,38,3C` | `0x03810030..3C` | `0x03820030..3C` |
| 写数据：四个 32 位字 | `+0x40,44,48,4C` | `0x03810040..4C` | `0x03820040..4C` |
| 每个 target 的两位状态 | `+0x78` | `0x03810078` | `0x03820078` |

提交前，代码读取 `base+0x08`，把旧值写回同一寄存器，并检查原值的 bit 0。写回是否清除状态尚未证明。`E927A` 取 `(value_at_0x78 >> (2*target)) & 3`；值为 1 或 2 时，除 opcode 3 外进入检查失败路径。不能据此直接把状态命名为 busy/error。

### 命令字段

`E7942` 对 `base+0x1C` 的旧命令字修改如下：

| 位 | 恢复出的内容 |
|---|---|
| `3:0` | opcode，读 `0`、写 `2` |
| `7:6` | `B & 3` |
| `8` | `flag & 1` |
| `10:9` | `A & 3` |
| `18:16` | `target & 7` |
| `28` | context 保存的每端口标志，取低一位 |
| `31` | 提交时置 1 |
| 其余位 | 保留旧值 |

可以独立转写为以下 32 位算式；这是格式说明，不是已验证可用的硬件操作程序：

```text
mask = 0x100707CF
fields = (B & 3) | ((flag & 1) << 2) | ((A & 3) << 3)
command = (old & ~mask)
        | (opcode & 15) | (fields << 6)
        | ((target & 7) << 16) | ((port_flag & 1) << 28)
        | 0x80000000
```

例如假设 old=0、port_flag=0、target=3、A=1、B=0、flag=0，则读命令字为 `0x80030200`，写命令字为 `0x80030202`。这只是转写算式的结果；并未在设备上发送。

### 地址字段

`E7A04..E7A10` 把调用者地址转换后写入 `base+0x20`：

```text
encoded = ((address & 0xF) | ((address >> 4) << 5)) mod 2^32
```

其效果是：保留源 bits 3:0，在输出 bit 4 插入零，源 bits 30:4 放到输出 bits 31:5；源 bit 31 在 32 位截断后不保留。示例：`0xF→0xF`、`0x10→0x20`、`0x01234567→0x02468AC7`。

目前未在此设置函数内发现地址范围检查，调用者可能施加更严格边界。该位运算不包含已经确认的 row/column/bank 字段名称，也不能推出全部介质容量。

## 4. 读写的具体执行顺序

**读路径：** `E7AFC` 以 opcode 0 调用提交函数，A 由调用者提供，B/flag 为零，提交时不提供写数据指针。`E7942` 先进行状态检查，再写入地址寄存器，最后写入命令寄存器。随后 `E7BF8` 轮询；返回非零后，`E7B4E/E7B54` 循环四次，从 `base+0x30+i*4` 原样复制到输出缓冲区。

这条数据读路径没有调用第二轮发现的 `E8FF0` 16 位响应重排函数。不能把配置寄存器响应的位排列直接套到这 16 字节数据上。

**写路径：** `E7A1C` 以 opcode 2 调用提交函数。`E79BC/E79C4` 循环四次，把源缓冲区的 32 位字复制到 `base+0x40+i*4`，再写地址和命令，随后轮询。若 flag 非零且轮询返回非零，会调用后续函数 `E7A6E`。

**后续操作：** `E7A6E` 使用 opcode `0xB`，依次向 port 索引 0、1 提交同一 target/address。观察到它轮询的却是原调用者 port；这里不能自行改写为“轮询当前循环 port”。`E7AB2` 版本在 opcode 2 提交成功后，调用轮询，再继续进入 `E7A6E`，在这两者之间没有检查轮询返回值。两个写流程的错误处理不能视为相同。

尚无足够证据给 `0xB` 命名为 program、commit 或 flush，也不能断言省略它仍可完成介质持久写入。

**完成条件：** `E7BF8` 检查状态 bit 0，要求连续十次置位。未置位的观察会把连续计数清零，并增加另一个累计“未置位”计数；该计数上限在这些调用中为 `0x6ACFC0`。它不是总轮询次数，也不是已确定的微秒数。完成位不等于已经确认 ECC 正确或掉电后数据仍然存在。

## 5. 为什么将其列为单元数据访问的重点候选

### 同地址写入图案、读回并计算差异

`E087E` 依次准备 `0x55AA55AA` 与 `0xAA55AA55` 图案。`E093A` 调用数据写入口 `E2C40`，之后经过延迟调用，`E097C` 用相同的目标映射和地址计算调用数据读入口 `E2B14`。`E0984..E09C0` 比较读回的全部四个字，分别计算预期为 1 而读为 0、预期为 0 而读为 1 的差异，并累计计数。

这确认了固件把两条通路作为成对的数据写入/读回操作使用。物理上是否必然直达阵列、是否经过硬件缓存或 ECC，仍需其他证据。

### 读出、按字节修改、写回

`C69A0` 在 `C69C0` 调用 `C6912`，读入 RAM 缓冲区 `0xB7680`。随后按调用者的位掩码，对选中的字节异或 `0xFF`，循环处理 16 字节；在 `C69F4` 调用 `C695A` 把修改后的缓冲区写回同一目标和地址。

这提供了另一条直接的数据流证据。该例程没有在读失败时立刻跳过后续写入，因此不能将它当成可直接复用的健壮读改写程序。

### 端口/目标映射和逐块访问

`C6912/C695A` 把 target-slot 映射为 `0x86838+slot` 的一个字节，再拆为 `port=(entry>>5)&7`、`target=entry&31`。低层范围检查分别为 2、8。`DA30A` 在初始化过程中为接受的目标建立这个表；它不只是随意给出的固定芯片索引。

VBUF 的 `40C8A8` 使用相同入口循环读或写。每次缓冲区指针增加 `0x10`，传输计数增加 1；设运行时目标数为 N，地址为 `start_address+floor(i/N)`，目标槽为 `start_slot+(i mod N)`。因此，软件以 16 字节为一个传输单元，并可在目标间轮转。这不证明物理存储单元或最小阵列读写粒度就是 16 字节。

## 6. 另一层内部命令记录已定位

VBUF `40C1EE` 是一个内部记录分派函数，参数为记录指针、port、target。记录首字的 selector 9、10、11 分别调用上述写、读、另一种写入口。数据缓冲区位于记录 `+0x0C`，长度 16 字节，选项位于 `+0x1C`。

若 `w1=word(record+4)`、`w2=word(record+8)`，它恢复的地址为：

```text
address = ((w1 & 0x03FFFFFF) << 4) | (w1 >> 30) | ((w2 & 3) << 2)
```

这里是内部记录编码，不是已确认的 NVMe 命令结构。还未追通主机如何构造或到达此记录，不能把 selector 9/10/11 直接当成外部可发送操作码。

继续离线研究时，优先从以下三个入口扩展：

1. **地址语义：** 上追 `C6912/C695A`、`40C8A8` 的调用者及内部记录构造者，查地址边界、掩码、移位、容量与几何参数来源。目标是把地址参数对应到阵列坐标，而非仅保留一个数值地址。
2. **写入与完整性：** 为所有到 `E7A6E` 和 opcode B 的调用建立交叉引用，比较 A/B/flag 与错误状态的用法；继续追踪 `E15B6` 周边的数据读取和配置状态访问，确定是否涉及 ECC、诊断模式或写入阶段。
3. **真实业务路径：** 追通正常请求调度、DMA/缓存和 LBA 转换是否调用同一引擎。若只发现诊断/训练入口，需要继续确认它对真实介质地址的覆盖范围。

现有结果足以锁定后续反汇编的主要入口，但不足以编写已经验证可用的裸芯片读写驱动。完整 PE、资源、签名和段提取资料在第一轮报告；PHY/配置寄存器规则在第二轮报告。本报告重点是新恢复的数据通路。

## 8. 验证与附件

所有关键调用和载入/存储指令都用独立静态反汇编片段复核。对地址打包算式检查了低 65,536 个输入及边界值；确认保留源 bits 30:0、输出 bit 4 为零、源 bit 31 不保留。对命令的 target/A/B/flag 字段做组合检查，确认掩码及位位置。上述检查验证数学转写一致性，不验证设备行为。

同目录 `raw_media_findings.json` 保存结构化结果，`data_register_fields.tsv` 保存窗口偏移用途。证据包收录本报告、定位表、原始字节切片、相关反汇编片段及校验值；不包含可执行的硬件访问工具。
