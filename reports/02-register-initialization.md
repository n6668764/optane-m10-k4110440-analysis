# K4110440 第二轮离线静态分析：寄存器访问与初始化配置

本轮已经从“找到相关字符串”推进到**恢复具体寄存器窗口、位重排、访问序列，以及 44 条条件化寄存器修改规则**。规则涉及 32 个不同寄存器编号。它们由固件代码实际引用和处理，是值得继续研究的初始化/配置资料。

仍未证实这些寄存器的物理名称、AHU14132 对应关系或 3D XPoint 外部接口完整时序。下面的“端口、寄存器、读写、脚本”等名称是根据代码行为给出的分析标签，不是芯片厂商文档中的正式名称。

分析对象仍是原 DLL 提取的同一固件，SHA-256：`0a42b2e10bd725f3eecdbdbf52fd4fc4c7581887a5fe94c0cecb3561f600a7ee`。只解析文件、反汇编并追踪常量/数据流；未执行 DLL、固件、目标模拟器或硬件命令。对下面数学表达式做的数值检查只运行独立转写的 Python 算式。

## 1. 寄存器窗口已解析出具体地址

`0xCF25E` 调用构造函数 `0xE74CC`，传入：

```text
r1 = 0x03810000   第一个端口窗口基址
r2 = 0x00010000   两个窗口之间的步长
r3 = 0x03800000   公共控制窗口基址
```

构造函数循环两次，分别把 `r1 + index*r2` 交给 `0xD2C70`；后者保存原基址。它把两个包装对象指针放在 `ctx+0x110` 和 `ctx+0x114`。另一个包装对象保存公共控制窗口。

这里也追通了全局对象链：`0xE74CC` 将 context 存入 `0x91194`；`0xCE8BA → 0xE2DB8` 取得它并绑定到包装对象，再把包装对象地址存入 `0x913C4`。此前的 `0xE2B48/0xE2B60` 正是通过该地址取得 context。因此，基址不再只是孤立的常量猜测。

| 窗口 | 地址 |
|---|---:|
| 公共控制窗口 | `0x03800000` |
| 索引 0 的窗口 | `0x03810000` |
| 索引 1 的窗口 | `0x03820000` |

这些是固件使用的控制器地址空间。没有证明它们是主机可访问的 PCI BAR 地址，也没有证明可以从 Windows 直接访问。

### 简单寄存器访问路径

读：`0xE2B48 → 0xE2E28 → 0xE7D5A`；写：`0xE2B60 → 0xE2E3A → 0xE8076`。

| 窗口内偏移 | 实际观察到的用途 |
|---|---|
| `+0x08` | 检查 bit 0，提交前和轮询时均读取 |
| `+0x1C` | 命令字：低四位读为 `0xC`、写为 `0xD` |
| `+0x20` | 读时写入 `selector<<16`；写时写入 `(selector<<16) OR value` |
| `+0x30` | 读回响应，取低 16 位并重排 |

命令还设置第二索引到 bits 18:16，清 bit 8，把每端口标志放到 bit 28，设置 bit 31。第一索引限制为 0–1，第二索引限制为 0–7。`0xE7BF8` 轮询 bit 0，要求连续十次观察到置位，计数上限由调用者提供；相关函数常用常量 `0x6ACFC0`。这些计数不是已经确定的微秒数。

## 2. 两套响应位重排已恢复

`0xE8FF0` 输入是低 16 位：第一索引为 0 时走第一套规则，非 0 时走第二套；函数没有使用 context 和第二索引参数。

表中每一行表示：**输入的这一位被放到输出的哪一位**。

| 输入 bit | 索引 0：输出 bit | 索引 1：输出 bit |
|---:|---:|---:|
| 0 | 7 | 0 |
| 1 | 5 | 2 |
| 2 | 3 | 4 |
| 3 | 1 | 6 |
| 4 | 0 | 7 |
| 5 | 2 | 5 |

| 10 | 11 | 12 |

| 13 | 10 | 13 |
| 14 | 12 | 11 |

对每套独立转写的移位/掩码表达式检查了全部 65,536 个 16 位输入：与表格一致，且每套都是一一对应的排列。`0x55AA` 经两套规则均得到 `0x9966`。

简单读函数先以 `UXTH` 截取响应低 16 位，再把它右移 16 位传给第一次转换，因此那次转换输入为零；最终结果的高 16 位为零，低 16 位来自上述排列。不能把 MMIO 读指令宽度直接当作设备寄存器数据宽度。

这说明固件明确处理了按第一索引变化的数据位顺序。它尚不能给出各个外部 DQ 引脚与位号的对应关系。

## 3. 一段完整的访问模式序列

`0xE1C78` 和低层版本 `0xE8D58` 都包含如下顺序：

```text
write(0x3E8, 0xCAFE)
write(0x3E8, 0xCA2E)
write(0x3E8, 0x1137)
write(0x3E8, 0x2BA0)
write(0x3E8, 0xDEAD)
delay_helper(1)
最多十次读取 0x3FE，检查 bit 15
```

前一个版本逐步检查写入函数返回值，失败会提前退出；后一个版本在写入失败路径上仍会进入延迟和状态检查，因此不能把两个版本的失败处理视为完全相同。状态 bit 15 控制轮询何时停止，但这里的最终返回值主要保留写入调用结果；不能把返回非零等同于该状态位必然置位。

`0xE8E04` 的结束操作是：`write(0x3FC, 0xBABA)`。固件在读取配置来源字段及应用规则前后使用这些操作。

其形态类似进入/退出某种寄存器访问模式，但尚无证据为它命名为厂商模式、解锁、安全认证或 PHY 专用模式。延迟函数参数 1 的单位也未确定。

## 4. 八个 5 位字段构成的另一条寄存器访问路径

应用条件表的函数没有直接使用简单 `0xC/0xD` 访问路径。它通过 `0xE192C` 构建读描述符、通过 `0xE18C6` 构建写描述符；继续下追到 `0xE8C46` / `0xE8B6E`，可见固件把字段装入控制器的脚本窗口，再以低四位为 `0xF` 的命令提交。

已恢复常用的八字段形式。设寄存器编号 `reg` 为 14 位，数据 `data` 为 16 位，读描述符的 operation nibble 为 9，写为 8：

```text
t0 = 2 * operation_nibble
t1 = 0
t2 = (reg >> 5) & 0x1F
t3 = reg & 0x1F
t4 = ((reg >> 10) & 0x0F) * 2 + ((data >> 15) & 1)
t5 = (data >> 10) & 0x1F
t6 = (data >> 5) & 0x1F
t7 = data & 0x1F
```

字段 `t0..t3` 放到 `base+0x24` 的四个字节低五位，`t4..t7` 放到 `base+0x28` 的四个字节低五位，保留字节中的其他位。写路径还会填入 `base+0x2C`，八字段形式下多出的槽位为零。提交命令中还有字段数、第二索引、每端口标志和调用者传入的模式/参数。

例如读 `0x7C8` 的八字段为：`[18, 0, 30, 8, 2, 0, 0, 0]`。

把 `0x7C8` 的目标值写为 `0x0540` 时：`[16, 0, 30, 8, 2, 1, 10, 0]`。

这是**控制器内部描述符和提交格式**。5 位字段可以成为继续识别外部接口编码的入口，但不能据此直接宣布总线就是五根数据线，或者外部芯片操作码就是 8/9。

## 5. 已提取 44 条条件化修改规则

原表在 PBUF 地址 `0xBA684`，PBUF 偏移 `0x684`，完整固件偏移 `0xA84`，原 DLL 文件偏移 `0xEAB54`。它有 44 条记录，每条 24 字节，共 1,056 字节。

原表 SHA-256：`ab3a5734881a87626bd862902063e7fd2560aa9fdba5f398377a0be1edb5afd4`。

消费者 `0xDBCEE` 明确按 24 字节步长遍历 44 次。字段布局已由读取指令验证：

```text
+0x00  u32  操作模式：0 设置，1 增加，2 减少
+0x04  u16  寄存器编号
+0x06  u16  设置值或增减量
+0x08  u16  字段掩码
+0x0A  u16  字段移位
+0x0C  u16  第一条件下限（含）
+0x0E  u16  第一条件上限（含）
+0x10  u32  第一条件来源选择：0 选 A，1 选 C
+0x14  u16  条件 B 下限（含）
+0x16  u16  条件 B 上限（含）
```

## 6. 初始化与训练线索的进一步限定

候选介质初始化入口 `0xDA3DA` 在相关分支中读 `0x100`，要求其低字节为 `0x89`；高字节经 `0xDAB68` 归入 0、1、2 类，存到上述全局状态。这里可以确认数值检查，不能凭 `0x89` 就确认外部芯片厂商。

读 `0x102` 后，低字节 1/2 分别被转成 `0x2000` / `0x4000`；`0x106` 的四个 nibble 被组合进两个配置字节；`0x101` 的低字节按目标索引保存。

`0xDAA74` 读取 `0x105` 的 bits 15:8，并收集四组 `(0x108+2*i, 0x109+2*i)`。有一个重要细节：它虽然先读 `0x102`，随后却把筛选变量设为常量 **`0x55`**，而非使用该读回值。逐次右移两位后，四组选择均为 1，因此本地流程预计收集四组结果；之后排序，并保留“数量不足 2 → TRAINING_FAILED”的判断。

所以，这一段更准确的描述是**训练相关结果采集/处理路径**。尚未证明它本身会扫描延迟、寻找眼图窗口或执行全部主动训练。不能仅凭 TRAINING_FAILED 字符串推断恢复了完整训练算法。

## 7. 本轮能确认什么，下一步针对什么

已经恢复：两个控制器窗口与公共基址、简单访问机制、16 位位排列、进入/退出访问模式的固定序列、八个 5 位字段的描述符形式，以及有实际消费者的 44 条条件配置规则。这些是我们需要的具体资料。

仍需解析：`0xF` 提交命令其余字段的正式含义、描述符字段如何驱动物理接口、寄存器位的芯片定义，以及 AHU14132 与这些地址的对应关系。

下一步最有价值的是沿 `0xE8B6E/0xE8C46`、其他描述符调用者以及 PLL/DQS 检查辅助函数，继续区分控制器内部设置和外部介质操作。也可以使用另一份匹配平台固件，对照本表和访问函数；当前附件只能证明这一版本中的具体代码和数据。

附件保留每段结论对应的反汇编、原始表、完整 JSON/TSV 规则与位映射。地址均是重建的固件地址空间；PBUF 中地址 v 对应原 DLL 文件偏移 `0xEA4D0 + (v-0xBA000)`。线性反汇编文件中的字符串和常量池会显示为伪指令，须按数据对待。
